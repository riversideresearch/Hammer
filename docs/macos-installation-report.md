# Hammer: macOS installation and portability report

Tested revision: `2592c90eed2851b84b1bc81d331648efd520aecd` (`bugfix/macOS`), Hammer 3.3.0.

The native C library builds and installs on Apple Silicon without source changes. Two issues remain: a compiler-dependent test assertion and a macOS shared-library install name that prevents normal execution outside the checkout. The documented pkg-config variant query also lacks implementation.

This report describes observed macOS behavior and source-level portability differences. Linux was not executed during this validation; Linux comparisons below are not claims of a reproduced Linux pass.

## 1. Failing test: source column assumes a compiler fallback

Test: `/core/parser/trace_with_context_owns_metadata`

Relevant source:

- `tests/backends/test_trace.c:762`: `test_with_context_owns_metadata()`.
- `tests/backends/test_trace.c:793`: unconditional assertion that the captured column is zero.
- `src/hammer.h:1692–1703`: compiler feature detection and `H_CONTEXT` expansion.

The test wraps a parser with `H_CONTEXT(parser, "udp.protocol.byte")`, checks the copied diagnostic metadata, and then asserts:

```c
g_check_cmp_size(outer->diagnostic_source->column, ==, 0);
```

Observed output:

```text
# Check failed: (outer->diagnostic_source->column == 0): (59 == 0)
not ok 40 /core/parser/trace_with_context_owns_metadata
Bail out!
scons: *** [build/opt/src/core_tests.stamp] Error 250
```

The top-level `scons test` command exited 2. The failing case also reproduced when run alone; all other 748 cases passed when invoked separately.

### Why this differs across compilers

`src/hammer.h` defines the source column according to compiler capabilities:

```c
#if defined(__has_builtin)
#if __has_builtin(__builtin_COLUMN)
#define H_CONTEXT_COLUMN() __builtin_COLUMN()
#endif
#endif

#ifndef H_CONTEXT_COLUMN
#define H_CONTEXT_COLUMN() 0
#endif
```

Apple Clang takes the builtin branch and produces column `59` at this macro expansion. The test expects the fallback branch regardless of compiler support. A compiler without this builtin uses zero and satisfies the assertion.

This is a compiler-feature distinction, not inherently a macOS-versus-Linux distinction: a Linux compiler supporting the same builtin may encounter the same assertion. The observed failure does not by itself show that metadata ownership is broken.

### Reproduction and suggested correction

From the repository root, using native tools:

```sh
scons test
```

To isolate the failure after the test executable has been built:

```sh
DYLD_LIBRARY_PATH="$PWD/build/opt/src" \
  build/opt/src/build/opt/test_suite \
  -p /core/parser/trace_with_context_owns_metadata
```

The duplicated `build/opt` segment is the executable path generated by this revision's SCons scripts.

Suggested correction: make the assertion conditional on the same builtin feature check, validating a nonzero column when supported and zero for the fallback. Avoid hard-coding `59`, since source formatting can change it. Retain the existing file, function, line, and ownership checks. Exercise both compiler-feature paths in CI where practical.

No test correction was applied during this validation.

## 2. Installed macOS dylib retains a relative build-tree identity

The installed shared library is ARM64 and links successfully, but an independently compiled consumer fails when launched outside the checkout.

Observed library identity:

```sh
otool -D /usr/local/lib/libhammer.dylib
```

```text
/usr/local/lib/libhammer.dylib:
build/opt/src/libhammer.dylib
```

Observed consumer failure:

```text
Library not loaded: build/opt/src/libhammer.dylib
Reason: tried: 'build/opt/src/libhammer.dylib' (no such file)
```

The consumer exited 134. Linking uses the library's recorded Mach-O install name; finding the file through `-L/usr/local/lib` at link time does not correct that name for runtime loading.

### Minimal consumer reproduction

After `scons install`, save this as `smoke.c` in a directory outside the checkout:

```c
#include <hammer/hammer.h>

int main(void) {
    const uint8_t input[] = {'a'};
    HParser *parser = h_ch('a');
    HParseResult *result = h_parse(parser, input, sizeof(input));
    if (!result) {
        h_parser_free(parser);
        return 1;
    }
    h_parse_result_free(result);
    h_parser_free(parser);
    return 0;
}
```

Compile and run from that directory:

```sh
export PKG_CONFIG_PATH="/usr/local/lib/pkgconfig${PKG_CONFIG_PATH:+:$PKG_CONFIG_PATH}"
cc smoke.c -o smoke $(pkg-config --cflags --libs libhammer)
./smoke
```

The equivalent installed static-library test passed:

```sh
cc smoke.c -I/usr/local/include /usr/local/lib/libhammer.a -lpthread -o smoke-static
./smoke-static
```

This temporary shared-library workaround also passed:

```sh
DYLD_LIBRARY_PATH=/usr/local/lib ./smoke
```

### Build-system implication

`src/SConscript` creates `SharedLibrary("hammer", ...)` and copies the resulting dylib with `env.Install`, without setting an installed identity. The resulting Mach-O identity names the build output.

Suggested correction: define a deliberate macOS install-name policy, either an installed absolute path consistent with `prefix` or an `@rpath` identity with documented consumer runpaths. Validate custom prefixes and staged installs when choosing that policy.

The Linux ELF runtime loader has different identity/search semantics; Linux link success is not sufficient validation of a Mach-O install name. No corresponding Linux failure was reproduced here.

The existing macOS test command sets `DYLD_LIBRARY_PATH` to the build directory, so it does not detect this installed-library problem. CI should compile and run a consumer against installed headers and libraries from outside the checkout, without a loader-path override.

## 3. Documented pkg-config variant query returns no value

The README recommends:

```sh
PKG_CONFIG_PATH=/usr/local/lib/pkgconfig pkg-config --variable=variant libhammer
```

The result is empty because `libhammer.pc.in` defines no `variant` variable. The version query correctly returns `3.3.0`.

This is a platform-independent documentation/metadata mismatch. Either export the selected variant in the generated metadata or remove the unsupported query.

## macOS setup differences worth documenting

| Area | macOS consideration | Linux comparison |
| --- | --- | --- |
| Prerequisites | Install Apple's Command Line Tools and use `brew install scons glib pkg-config`, matching the macOS CI job | README's `apt` commands target Debian/Ubuntu |
| Compiler selection | Apple's `gcc` command is Clang; inspect compiler capabilities rather than its executable name | A Linux `gcc` command may be GNU GCC; builtin availability still depends on the compiler/version |
| Apple Silicon architecture | Keep the compiler, Python/SCons, pkg-config, and dependency libraries native ARM64; native Homebrew normally uses `/opt/homebrew` | Architecture consistency is required on either OS; Rosetta adds a macOS-specific source of mismatches |
| Runtime search | Use Mach-O install names and `DYLD_LIBRARY_PATH` for the verified workaround | The build scripts select `LD_LIBRARY_PATH` on non-Darwin platforms; Linux ELF loading needs separate validation |
| Platform APIs | This branch uses `_DARWIN_C_SOURCE` and omits `-lrt` on Darwin | The non-Darwin branch uses `_POSIX_C_SOURCE=200809L` and links `-lrt` |
| Installation prefix | Hammer still defaults to `/usr/local`, independently of Homebrew's prefix; expose its `lib/pkgconfig` directory explicitly if needed | A package-manager prefix and the library's chosen install prefix need not coincide |

On Apple Silicon, a Rosetta shell can report `x86_64` and select an Intel Homebrew under `/usr/local`. Useful checks are:

```sh
uname -m
sysctl -n hw.optional.arm64
sysctl -n sysctl.proc_translated
command -v brew pkg-config scons
file /usr/local/lib/libhammer.dylib
```

In the observed translated session, the two sysctl queries returned `1` and `1`: ARM64 support and active translation. Explicit native execution resolved the architecture mismatch:

```sh
export PATH="/opt/homebrew/bin:/opt/homebrew/sbin:$PATH"
arch -arm64 /opt/homebrew/bin/scons
arch -arm64 /opt/homebrew/bin/scons install
arch -arm64 /opt/homebrew/bin/scons test
```

The final command still reproduces the test failure above. No additional Hammer-specific libraries were required beyond the documented build/test prerequisites; Homebrew installed Python and supporting libraries transitively.

## Recommended developer follow-up

1. Correct the source-column test's compiler-feature assumption and validate it with both Clang and GCC.
2. Correct the installed dylib identity and add an installed-consumer smoke test to macOS CI.
3. Resolve the pkg-config variant documentation mismatch.
4. Document native Apple Silicon tool selection and macOS prerequisite commands alongside the Linux instructions.

Language bindings, debug/coverage variants, Linux execution, and native Intel macOS execution were not validated. No Hammer source changes were made as part of this report.
